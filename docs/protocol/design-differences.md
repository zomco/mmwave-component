## 3. Category C Decision Record & Implementation Details (User Approved)

### 3.1 `DD-07`: Per-Field `expected_interval_ms` and `stale_after_ms` in R60ABD1 Capability Descriptors
- **Background & G0 Hardware Evidence**:
  - Draft Section 5 used `position.xy: { expected_interval_ms: 2000, stale_after_ms: 6000 }` as an illustrative example, noting it required hardware verification and could remain `null` if unspecified.
  - During the G0-03 2-hour hardware endurance test (`7,199.8 s`), we obtained exact hardware measurements:
    1. `R60ProbeStats::target_observations` (which counts only R60 `0x80/0x05` 2D XY coordinate frames) increased from `14` to `3,613` (`+3,599` frames over `7,199.8 s`), proving that **R60ABD1 hardware reports `position.xy` at an exact `2,000 ms` (`0.50 Hz`) interval**.
    2. `R60ProbeStats::valid_frames` (which aggregates heartbeat, presence `0x80/0x01`, motion `0x80/0x02`, body movement `0x80/0x03`, distance `0x80/0x04`, XY position `0x80/0x05`, breath, heart rate, and sleep control words) increased by `34,878` frames (mean **`4.84 Hz`**, `4..8 frames/s`). Because the G0 probe did not bucket non-`0x80/0x05` control words individually, separate hardware intervals for `presence`, `breath_rate`, and `heart_rate` were not individually bucketed in G0.
- **Evaluated Options**:
  - **Option C1**: Keep `"expected_interval_ms": null, "stale_after_ms": null` across all observation features in `docs/protocol/fixtures/r60abd1-capabilities.json`.
  - **Option C2 (User Approved & Adopted)**: Set `position.xy` in `r60abd1-capabilities.json` and `simulator.js` to `"expected_interval_ms": 2000, "stale_after_ms": 6000`, keeping other event-driven/unbucketed fields `null`.
  - **Option C3**: Add per-control-word counters in the WP-2 R60 Adapter and populate all intervals at G2.
- **Final Status**: **Approved by User (Option C2) & Applied** across `docs/protocol/fixtures/r60abd1-capabilities.json`, `static/src/protocol/simulator.js`, and `static/test/protocol-schema.test.js`.

### 3.2 `DD-08`: Allowed Range for R60ABD1 Installation Height `install.z_cm` (`50..400 cm` vs Synchronously Widened `50..600 cm`)
- **Background & Evidence**:
  - In `tests/common/r60abd1.yaml`, the Home Assistant `num_radar_z` Number entity was originally `min_value: 50, max_value: 400, step: 1` (`cm`), while `components/r60abd1/__init__.py` compile-time YAML schema allows any positive float.
- **Evaluated Options**:
  - **Option C1**: Keep `install.z_cm` at `50..400 cm` (step `1`).
  - **Option C2 (User Approved & Adopted)**: Synchronously widen upper bound to `50..600 cm` (step `1`) across `tests/common/r60abd1.yaml` (`num_radar_z`), `docs/protocol/fixtures/r60abd1-capabilities.json`, and `static/src/protocol/simulator.js`.
- **Final Status**: **Approved by User (Option C2: `50..600 cm`) & Synchronized Across All Three Targets** (verified in `static/test/protocol-schema.test.js` with `install.z_cm = 600` accepted and `601` rejected as `OUT_OF_RANGE`).

## 4. Explicit v1 Scope Exclusions (Closed)
1. `AUTH_REQUIRED` is not an MWCP/1 error code (v1 relies on the physical local USB trust boundary).
2. R60ABD1 local Z output is exposed solely as `diagnostics.local_z` and does not make R60ABD1 a 3D point-cloud product.
3. `inject_mock_data` and `raw_uart_tx` are not MWCP/1 production actions and must never be enabled in release firmware.
